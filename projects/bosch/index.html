03 / Professional Project Bosch

Billing Intelligence Platform

I led the design and build of a billing platform that connected source data, user corrections, invoicing and reporting in one workflow.

Role
Business Intelligence Intern

I owned the implementation from data preparation to the application workflow. I connected the source systems, built the billing logic, defined what users could correct, and made sure approved changes flowed back into invoicing and reporting.

MongoDBAzure SQLPower Query Power BIDataversePower Apps Billing Automation
Confidentiality

System details and business data are anonymized. The workflow and project story reflect the work I completed.

01 / Problem

I started with a billing process that depended too much on manual work.

Teams had to bring together usage data, apply billing rules, investigate differences, correct records and prepare invoices. A lot of that work depended on spreadsheets and individual knowledge.

The problem

The same billing work had to be checked and repeated manually.

That made the process harder to keep consistent across teams and business units.

My decision

Let users fix defined billing issues without giving them access to everything.

I built the workflow so approved fields could be corrected while the rest of the data stayed protected.

02 / Platform design

I connected the billing steps instead of treating them as separate tools.

Source data came from MongoDB and Azure SQL, Power Query prepared it, Dataverse stored the working billing records, Power Apps handled user corrections, and Power BI showed the result.

SourceMongoDB + Azure SQL
PreparePower Query
StoreDataverse
CorrectPower Apps
ReportPower BI

Corrections: Approved changes were stored in Dataverse and used by the billing and reporting flow.

Use: The application was used across multiple business units instead of separate billing files.

03 / Data control

I controlled what users could change and what had to stay protected.

Business users could correct known billing issues directly in the application, but only through approved fields and checks. The corrected record stayed in Dataverse and continued through the same billing flow.

Controls I built

Editable fieldsOnly approved billing fields could be changed.
ChecksRequired values and billing rules were checked before saving.
Stored changesCorrections were saved in Dataverse instead of separate user files.
Change historyChanges could be followed through the correction and billing process.
ReportingUpdated values returned to planned versus actual reporting.
Key idea

The corrected record stayed connected to billing and reporting.

Users did not need separate correction files. The approved change stayed in the same data flow used for invoice preparation and reporting.

04 / What I built

I owned the work across the data, application and billing flow.

I translated the billing process into system rules, connected the tools, built the correction workflow and decided which changes users could make themselves.

01

Built the billing logic

I mapped the source data and billing rules into a structure that supported correction, invoicing and reporting.

02

Connected the data flow

I connected MongoDB, Azure SQL, Power Query, Dataverse, Power Apps and Power BI.

03

Built user corrections

I defined which fields could be edited, added checks and stored approved changes in Dataverse.

04

Closed the reporting loop

I sent the corrected billing state back into planned versus actual reporting.

Key decision

I did not give users open access to every field. Only billing fields that could be safely corrected were editable. Other changes stayed with the analyst team.

This kept the application useful for the business while protecting the data used for invoicing.

05 / Billing flow

I connected the full path from finding a billing issue to confirming the final result.

A user could find a difference in reporting, review the record, correct an approved field, continue the billing process and then see the updated result in reporting.

How the workflow worked

1
Find

Planned versus actual reporting showed a billing difference.

2
Review

The user checked the record and the billing details behind it.

3
Correct

Approved fields were changed in Power Apps and saved to Dataverse.

4
Invoice

The corrected record continued into the invoice process.

5
Confirm

The final billing state returned to planned versus actual reporting.

06 / Outcome

I moved billing from separate manual steps into one connected workflow.

The platform gave teams one path from source data to correction, invoicing and reporting. Defined billing issues could be handled in the application while the underlying data stayed controlled.

Before

Billing depended on manual checks and separate files.

  • Repeated manual reconciliation
  • Knowledge held by individual users
  • Corrections handled outside the main data flow
  • Repeated handoffs between analysts and business users
  • Harder to follow a billing issue through to the invoice
After

The platform connected the repeatable billing work.

  • One consistent data preparation flow
  • Controlled corrections through Dataverse and Power Apps
  • Corrected records connected to invoicing
  • Business users handled defined issues directly
  • Reporting reflected the final billing state
Project takeaway

The value was not another dashboard. It was connecting reporting to action.

I built the platform so a billing issue could be found, corrected, used for invoicing and checked again without moving the record into separate files.
