02 / Professional Project ZEISS

Automated Freight Invoice Ingestion Pipeline

I led the design and build of a pipeline that turned freight invoices from different carriers and formats into structured data ready for reporting.

Role
Data Engineer Intern
Global Supply Chain

I owned the pipeline from document intake to SQL output. I designed how invoices were routed, chose the extraction method for each format, built the processing logic, and added validation so failed or unclear invoices were sent for review instead of entering reporting.

Python spaCy Regex Azure Functions Azure SQL Power BI
Confidentiality

Invoice layouts, carrier names, field names and production volumes are anonymized. The pipeline flow reflects the work I completed.

01 / Problem

I started with the part that made automation difficult: every invoice looked different.

Freight invoices arrived as PDFs and spreadsheets from different carriers. People had to open them, find the right fields, and copy the information into Excel. The main problem was not reading one invoice, it was handling different layouts without sending bad data into reporting.

The problem

One fixed parser would not work across every format.

Field names, positions and document quality changed between carriers, so one set of positional rules would break as formats changed.

My decision

Make extraction flexible, but keep validation strict.

I separated document extraction from data validation so the pipeline could support different formats without lowering the quality of the final records.

02 / Pipeline design

I built the pipeline as separate steps so each part could be changed without breaking the rest.

Invoices entered through the same flow, but extraction could change by document type. After extraction, every result passed through the same validation and SQL output steps.

InputPDF / Excel invoices
TriggerAzure Functions
ExtractspaCy NER / Regex
ValidateSchema + business rules
PersistAzure SQL → Power BI

If extraction or validation failed, the invoice was sent for review instead of being written into the reporting data.

03 / Extraction

I used different extraction methods for different invoice structures.

I used spaCy when fields moved around in the document and Regex when a carrier format was stable enough for clear rules. Both paths produced the same set of output fields.

Changing layouts with spaCy

For fields that could appear in different positions or surrounding text.

NLP Extract fields from variable text

I used named-entity extraction where fixed positions were not reliable.

Normalization Map to shared fields

Carrier-specific labels were converted into the same freight-data fields used by the rest of the pipeline.

Stable layouts with Regex

For carrier formats that followed a consistent structure.

Rules Use carrier-specific rules

I used explicit patterns where the document structure was stable and easier to debug with rules.

Pre-processing Clean the text first

Common formatting differences were cleaned before the extraction rules ran.

04 / Validation

I treated validation as a required step, not a check at the end.

Extracted data was only saved after it passed required-field, type, logic and duplicate checks. Anything unclear stayed outside the reporting data until it could be reviewed.

Checks before saving

Required fieldsInvoice IDs, dates, references and core charge fields had to be present.
Schema
Data typesDates, charges and currencies had to be converted into the expected format.
Type
Field logicRelated values were checked for combinations that did not make sense.
Logic
DuplicatesInvoice and reference keys were checked before a new record was saved.
Integrity
Unclear resultsMissing, conflicting or uncertain results were sent for review.
Quality
Exception handling

A failed invoice stayed visible and could be run again.

I recorded where the invoice failed and why, so the issue could be reviewed, corrected and reprocessed without allowing bad data into reporting.

05 / Standard output

I mapped different carrier formats into one data structure.

Carrier labels could be different, but the reporting layer needed the same fields every time. I standardized the extracted values before they were saved to Azure SQL.

Different source labels

Carrier A“Freight Amount”, “Shipment Ref”, “Route”
Carrier B“Transport Cost”, “Consignment”, “Lane”
Carrier C“Charge”, “Waybill”, “Origin / Destination”
SpreadsheetStructured columns with inconsistent naming and ordering.

One output structure

invoice_idNormalized invoice identifier
shipment_referenceShared shipment / consignment key
freight_costStandardized charge field
currencyNormalized currency code
origin / destinationCommon route dimensions
validation_statusValidated / review / failed
06 / Running the pipeline

I made failures easy to find, fix and run again.

The pipeline recorded each document's processing stage and failure details. That made recurring format or parser issues easier to trace without handling them outside the pipeline.

What I tracked

StatusWhere the invoice was in the flow: received, extracted, validated, saved or failed.
Failure detailsWhich document failed, at which step, and what type of error occurred.
ReprocessingAfter a fix, the invoice could be sent through the same pipeline again.

Why this mattered

Daily use

The pipeline needed to handle problems without hiding them.

Keeping the failure details made new invoice formats and parser issues easier to identify, correct and reprocess.

07 / Outcome

I replaced repeated invoice transcription with a reusable ingestion process.

The pipeline turned different freight documents into validated, structured SQL records that could be used for freight-cost, route and operations reporting.

Before

Invoice processing depended on manual work.

  • Open and interpret invoices one by one
  • Handle each carrier format manually
  • Copy fields into spreadsheets
  • Resolve errors outside a standard process
  • Prepare the same data again for reporting
After

The pipeline handled the repeatable work.

  • Trigger invoice processing automatically
  • Choose extraction logic by document format
  • Map different labels into shared fields
  • Validate records before saving
  • Keep failed invoices separate for review
  • Write structured data to Azure SQL for reporting
Project takeaway

Automating the extraction was only half the job. The data also had to be safe to use.

I built the solution around that idea: use the extraction method that fit the invoice, convert the result into one structure, validate it before saving, and keep failures visible so they could be fixed and run again.
